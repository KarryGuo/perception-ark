## 1. 产品概述

### 1.1 产品定义

PerceptionArk（感知方舟）是一款专为视障人群设计的 AI 感知眼镜。产品将广角摄像头、麦克风阵列、IMU 传感器和骨传导模块集成在一副钛合金眼镜中，通过 TRAE 平台编排五个专业 AI 智能体，为视障者提供场景感知、导航引导、安全预警、社交辅助和环境记忆五重能力。

佩戴者不需要学习任何新交互方式——戴上眼镜，AI 自动感知周围环境并通过骨传导耳机以语音播报。用户也可以用自然语言发出指令，如"带我去超市""读一下这个"，系统通过 TRAE 的意图识别能力自动路由到对应智能体执行。

### 1.2 核心差异化

现有视障辅助产品（OrCam、Envision）均采用单模型串行架构，无法在导航播报中紧急插入安全预警。PerceptionArk 的核心创新在于：

- **五智能体并行协作**：每个 Agent 专注一个感知域，通过中央 Orchestrator 统一调度
- **优先级抢占机制**：安全预警 Agent 拥有最高优先级，可以在任何时刻打断其他 Agent 的输出，将紧急信息立即传达给视障者
- **端云三级降级**：云端完整 → 边缘降级 → 离线保命，任何网络条件下安全能力不中断
- **环境记忆**：系统学习用户的常用路线、熟人面孔和生活偏好，越用越懂用户

### 1.3 价值主张

**让黑暗有光。** 0.5 秒的差别，就是站着和躺着的区别。感知方舟不是锦上添花的工具，而是视障者独立出行的安全底线。

## 2. 市场与用户分析

### 2.1 市场规模

中国有超过 **1700 万** 视障人群 [数据来源：中国残联]。他们看不见红绿灯、认不出对面走来的是谁、读不了药盒上的说明书。导盲犬全国不足 5 万只，覆盖率不到 **0.3%**——绝大多数视障者的出行安全没有任何技术保障。

全球视障人群超过 **2.2 亿**（WHO 数据），其中大部分生活在发展中国家，无力承担动辄数万元的辅助设备。

### 2.2 竞品分析

| 维度 | OrCam MyEye | Envision Glasses | 感知方舟 |
|------|-------------|------------------|---------|

| AI 架构 | 单模型串行 | 单模型串行 | 五智能体并行协作 |
| 安全预警 | 无优先抢占 | 无优先抢占 | P0 优先级抢占 |
| 离线能力 | 不支持 | 不支持 | 三级降级 + 离线保命 |

OrCam 和 Envision 的核心局限在于价格门槛极高，且单模型架构无法实现紧急打断。感知方舟通过多智能体架构实现维度优势，同时以 ¥1,200 的 BOM 目标将可及性提升一个数量级。

### 2.3 目标用户

**核心用户**：全盲及重度弱视人群（视力 < 0.05），年龄 18-75 岁，有独立出行需求但缺乏安全辅助手段。

**次级用户**：视障者家属——需要实时了解家人位置和安全状态，在跌倒等紧急事件发生时第一时间收到通知。

**使用场景**：户外出行（通勤、购物、就医）、社交互动（识别熟人、读取菜单）、紧急安全（车辆避让、跌倒呼救）。

### 2.4 用户痛点（基于 5 位视障用户深度访谈）

1. **出行安全无保障**："过路口的时候不知道什么时候能走，经常被车按喇叭。"
2. **信息获取困难**："餐厅菜单看不了，药盒说明书读不了，很多东西只能靠摸。"
3. **社交尴尬**："有人跟我打招呼，我不知道是谁，只能尴尬地笑笑。"
4. **跌倒后孤立无援**："上次在家里摔了一跤，趴在地上半小时才摸到手机。"
5. **辅助设备太贵**："OrCam 要两万多，买不起。导盲犬排队要等三五年。"

## 3. 产品架构

### 3.1 整体架构

系统分为四层，自下而上依次为：

```
┌─────────────────────────────────────────────────────┐
│                   输出层 (Output)                     │
│  骨传导语音播报 · 镜腿震动 · 家属端App通知 · SOS呼叫   │
├─────────────────────────────────────────────────────┤
│              多智能体协作层 (Multi-Agent)              │
│  ┌─────────────────────────────────────────────┐    │
│  │          Orchestrator 中央调度               │    │
│  │  任务分发 · 优先级仲裁 · 冲突消解 · 上下文管理 │    │
│  └─────────────────────────────────────────────┘    │
│  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐│
│  │  A01   │ │  A02   │ │  A03   │ │  A04   │ │  A05   ││
│  │场景感知│ │导航引导│ │安全预警│ │社交辅助│ │环境记忆││
│  └────────┘ └────────┘ └────────┘ └────────┘ └────────┘│
├─────────────────────────────────────────────────────┤
│              端云协同层 (Edge-Cloud)                  │
│  云端大模型 · 端侧NPU轻量模型 · 离线缓存 · 降级引擎    │
├─────────────────────────────────────────────────────┤
│               硬件层 (Hardware)                      │
│  广角摄像头 · 麦克风阵列 · IMU六轴 · 骨传导 · 蓝牙5.2  │
└─────────────────────────────────────────────────────┘
```

### 3.2 数据流

1. 传感器采集：摄像头每 500ms 抓取一帧，IMU 以 100Hz 持续采集加速度和角速度，麦克风持续监听
2. 端侧预处理：NPU 运行轻量目标检测（YOLO-nano），过滤出需要云端处理的帧
3. Orchestrator 路由：根据帧内容判断优先级，将数据分发到对应 Agent
4. Agent 推理：各 Agent 调用 TRAE 编排的工具链完成推理
5. 输出合成：推理结果通过流式传输到骨传导语音合成模块
6. 紧急抢占：安全预警 Agent 的输出拥有最高优先级，可中断任何正在进行的播报

## 4. 多智能体系统设计

### 4.1 智能体概览

| Agent | 名称 | 核心职责 | 优先级 | 触发条件 |
|-------|------|---------|--------|---------|
| A01 | 场景感知 | 环境描述、物体识别、路面状况 | P2 | 每3秒自动 / 语音提问 |
| A02 | 导航引导 | 路径规划、公交信息、转向提示 | P2 | 用户指令 / 定时播报 |
| A03 | 安全预警 | 车辆检测、障碍物测距、跌倒检测 | P0 | 实时持续 |
| A04 | 社交辅助 | OCR 文字识别、人脸识别 | P1 | 用户指令 / 场景触发 |
| A05 | 环境记忆 | 常用路线学习、熟人面孔记忆、生活偏好 | P3 | 后台异步 |

### 4.2 Orchestrator 中央调度

Orchestrator 是系统的中枢神经，承担四项核心职能：

**任务分发**：接收传感器数据流，根据内容类型路由到对应 Agent。摄像头检测到车辆时路由到 A03，检测到文字时路由到 A04，检测到路面异常时路由到 A01。

**优先级仲裁**：当多个 Agent 同时请求输出时，按优先级排序。A03（安全预警）拥有 P0 最高优先级，可以在任何时刻打断其他 Agent 的播报。例如 A02 正在播报"请直行15步"时，A03 检测到右侧电动车快速接近，Orchestrator 立即挂起 A02 的输出，将 A03 的"注意！右侧有电动车快速接近"以最高音量播报，同时触发镜腿高频震动。

**冲突消解**：当 A01 和 A03 对同一物体给出不同判断时（如 A01 认为前方是"停放的自行车"，A03 认为是"移动的电动车"），以安全优先原则采纳 A03 的判断。

**上下文管理**：维护一份共享环境状态，包括当前 GPS 位置、场景类型（室内/室外/路口）、最近危险事件、用户当前活动等。各 Agent 读取共享上下文做出更精准的判断，避免重复推理。

### 4.3 Agent 详细设计

#### A01 场景感知 Agent

- **输入**：摄像头帧（500ms 间隔）
- **输出**：环境描述文本 → 语音播报
- **工具链**：视觉理解 API（豆包多模态大模型）、物体分类器、路面状况检测器
- **典型场景**：用户出门时播报"早安。今天多云，气温24度。门口路面干燥。左前方3米处有一辆共享单车，注意避让。电梯已到达本层。"
- **降级行为**：云端模式下调用多模态大模型输出丰富描述；边缘模式下降级为物体标签列表 + 距离信息

#### A02 导航引导 Agent

- **输入**：GPS 位置、用户语音指令（"带我去超市"）
- **输出**：路径规划 + 转向提示 → 语音播报
- **工具链**：地图 SDK（高德/百度）、路径规划 API、公交信息查询
- **典型场景**："路径已规划。请直行15步到达公交站。326路公交车预计2分钟后到站。"
- **降级行为**：云端模式下调用在线导航；边缘模式下使用缓存的离线地图 + 步数推算

#### A03 安全预警 Agent

- **输入**：摄像头帧（100ms 间隔，高频）、IMU 数据（100Hz）
- **输出**：紧急告警 → 高音量语音 + 镜腿震动
- **工具链**：YOLO 目标检测（端侧 NPU）、单目测距、IMU 跌倒检测算法
- **典型场景**："注意！右侧有电动车快速接近，距离5米，请立即向左避让！"
- **降级行为**：安全预警是唯一在所有三种模式下都不中断的 Agent。云端模式下使用完整模型；边缘和离线模式下使用端侧 NPU 的 YOLO-nano + IMU 检测

#### A04 社交辅助 Agent

- **输入**：摄像头帧（用户触发）、用户语音指令（"读一下这个"）
- **输出**：OCR 文本 / 人脸识别结果 → 语音播报
- **工具链**：OCR API（百度/腾讯）、人脸识别 API、本地人脸特征库
- **典型场景**："菜单识别完成：红烧排骨饭 ¥28，宫保鸡丁饭 ¥22，番茄牛腩面 ¥18。上次您点过宫保鸡丁。"
- **降级行为**：云端模式下使用完整 OCR 和人脸识别；边缘模式下使用端侧轻量 OCR，人脸识别降级为本地特征匹配

#### A05 环境记忆 Agent

- **输入**：各 Agent 的历史输出、用户行为日志
- **输出**：记忆检索结果 → 上下文注入其他 Agent
- **工具链**：本地向量数据库（FAISS/Milvus Lite）、习惯学习模型、路线聚类算法
- **典型场景**：用户走到熟悉路口时，A05 向 A02 注入"这条路您过去30天走过18次，通常在这里等326路公交"
- **隐私边界**：所有记忆数据仅存于眼镜端本地，不云端同步，恢复出厂设置即清除

### 4.4 优先级抢占机制

这是系统最核心的创新点。当安全事件发生时，抢占流程如下：

```
时间线：
t=0ms   A02正在播报："请直行15步到达..."
t=50ms  A03检测到右侧电动车，距离5米，快速接近
t=60ms  A03向Orchestrator发送P0抢占请求
t=70ms  Orchestrator挂起A02输出队列，标记A02为"被抢占"
t=80ms  A03输出直达语音合成模块，最高音量播报
t=90ms  镜腿震动模块触发高频震动
t=2000ms A03播报完成，Orchestrator恢复A02被挂起的输出
```

从检测到危险到视障者听到告警，全链路延迟 < 200ms（端侧 NPU 本地推理，不依赖网络）。

## 5. TRAE 技术架构

### 5.1 TRAE 能力映射

感知方舟深度利用 TRAE 平台的六大核心能力，每个能力映射到系统的具体环节：

| TRAE 能力 | 映射环节 | 具体应用 |
|-----------|---------|---------|
| 多智能体编排 (Agent Orchestration) | Orchestrator 中央调度 | 定义五个 Agent 的角色、工具集和协作协议，通过 TRAE 任务分发机制路由感知数据 |
| 上下文管理 (Context Management) | 跨 Agent 状态共享 | 维护共享环境状态（GPS、场景类型、最近危险事件），各 Agent 读取避免重复推理 |
| 流式输出 (Streaming Output) | 实时语音播报 | Agent 推理结果流式传输到语音合成模块，首字输出 < 500ms |
| 意图识别 (Intent Recognition) | 语音指令理解 | "带我去超市"解析目的地实体触发导航，"读一下这个"触发 OCR |
| 多轮对话 (Multi-turn Dialogue) | 上下文连续交互 | "前方是什么？""是药店。""帮我读招牌。"——基于上轮播报追问 |
| MCP 工具调用 (Tool Calling) | 各 Agent 专业能力 | 视觉理解 API、地图 SDK、OCR、人脸识别、向量库——TRAE 统一管理工具注册与调用 |

### 5.2 TRAE Agent 编排设计

在 TRAE 平台中，五个 Agent 的编排配置如下：

**Agent 注册**：每个 Agent 在 TRAE 中注册为一个独立 Agent 实体，包含角色定义（system prompt）、工具集（tool list）和输出格式（output schema）。

```
Agent 注册示例（伪代码）：

Agent A03_Safety:
  role: "你是视障者的安全守护者。你的唯一任务是检测并预警危险。"
  priority: P0  # 最高优先级，可抢占任何Agent
  tools:
    - yolo_detect        # 端侧目标检测
    - distance_estimate  # 单目测距
    - imu_fall_detect    # IMU跌倒检测
  output: "紧急告警文本，不超过30字，必须包含方向+物体+距离+动作建议"
  trigger: "每100ms自动触发，或IMU检测到异常加速度时立即触发"

Agent A01_Scene:
  role: "你是视障者的眼睛。描述周围环境，帮助用户理解世界。"
  priority: P2
  tools:
    - vision_understand  # 豆包多模态大模型
    - object_classify    # 物体分类
    - road_condition     # 路面状况检测
  output: "环境描述文本，50-100字，包含天气、路面、物体、距离信息"
  trigger: "每3秒自动触发，或用户语音提问时触发"
```

**Orchestrator 编排逻辑**：

Orchestrator 本身也是一个 TRAE Agent，它的角色是协调者。它接收所有传感器数据，决定数据路由方向，并管理 Agent 间的上下文传递：

```
Orchestrator:
  role: "你是感知方舟的中央调度器。根据传感器数据决定激活哪个Agent。"
  manages: [A01, A02, A03, A04, A05]
  shared_context:
    - current_location    # GPS位置
    - scene_type          # indoor/outdoor/intersection
    - last_danger_event   # 最近危险事件
    - user_current_activity  # walking/waiting/reading
  arbitration_rules:
    - "A03拥有P0优先级，可抢占任何Agent"
    - "A04和A05不得打断A01/A02的播报"
    - "同一时刻最多1个Agent输出语音"
    - "被抢占的Agent输出挂起，待高优先级播报完成后恢复"
```

### 5.3 MCP 工具链设计

每个 Agent 通过 MCP（Model Context Protocol）调用外部工具。TRAE 统一管理工具注册、权限控制和调用日志：

| Agent | MCP 工具 | 工具类型 | 调用方式 |
|-------|---------|---------|---------|
| A01 | vision_understand | 云端 API | 豆包多模态大模型，输入图片帧，输出场景描述 |
| A01 | road_condition | 端侧模型 | 路面分类（干燥/湿滑/积水/台阶），NPU 本地推理 |
| A02 | map_navigation | 云端 API | 高德地图路径规划 SDK |
| A02 | bus_info | 云端 API | 公交实时到站信息查询 |
| A03 | yolo_detect | 端侧模型 | YOLO-nano 目标检测，NPU 本地推理，延迟 < 50ms |
| A03 | distance_estimate | 端侧算法 | 单目摄像头测距，基于物体边界框估算 |
| A03 | imu_fall_detect | 端侧算法 | 六轴 IMU 加速度阈值 + 模式匹配 |
| A04 | ocr_recognize | 云端 API | 百度 OCR 文字识别 |
| A04 | face_recognize | 云端+端侧 | 云端人脸比对 + 端侧本地特征库匹配 |
| A05 | vector_search | 端侧数据库 | FAISS 本地向量检索 |
| A05 | route_cluster | 端侧算法 | GPS 轨迹聚类，提取常用路线 |

### 5.4 流式输出架构

TRAE 的流式响应能力是低延迟语音播报的关键：

```
传统模式（非流式）：
Agent推理完成(3s) → 语音合成(1s) → 播报开始
总延迟：4s

TRAE流式模式：
Agent推理开始 → 首token生成(200ms) → 语音合成流式开始(100ms) → 播报开始
总延迟：300ms（首字）
```

Agent 推理结果以 token 流的形式传输到语音合成模块，实现"边推理边播报"。云端 4G 网络条件下，场景描述的首字输出延迟 < 500ms。端侧安全预警走 NPU 本地推理通路，延迟 < 200ms。

### 5.5 意图识别与多轮对话

视障者通过语音与系统交互。TRAE 的意图识别能力解析自然语言指令，无需固定话术：

- 用户说"带我去超市" → TRAE 解析目的地实体"超市" → 触发 A02 导航 Agent
- 用户说"读一下这个" → TRAE 识别 OCR 意图 → 触发 A04 社交辅助 Agent
- 用户说"前方是什么" → TRAE 识别场景询问意图 → 触发 A01 场景感知 Agent

多轮对话保持上下文连续性：

```
用户："前方是什么？"
A01："前方是一家药店，门口有三级台阶。"
用户："帮我读一下招牌。"
A04："招牌写着：老百姓大药房，营业时间8:00-22:00。"
用户："附近有超市吗？"
A02："距离您200米有一家联华超市，需要导航过去吗？"
```

TRAE 维护对话上下文，第三轮的"附近"基于第一轮识别出的药店位置进行推理。

## 6. 端云协同与降级策略

### 6.1 三级降级架构

视障感知是生死攸关的实时场景——0.5 秒的延迟可能意味着一辆电动车已经撞上。系统从架构层面设计了端云协同和三级降级策略，确保任何网络条件下都不失能。

| 等级 | 名称 | 网络状态 | 运行模式 | 安全能力 |
|------|------|---------|---------|---------|
| LEVEL 1 | 云端完整 | 网络畅通 | 五 Agent 全功能运行 | 完整（云端大模型） |
| LEVEL 2 | 边缘降级 | 网络不稳定 | 端侧轻量模型 + 核心 Agent 保活 | 完整（端侧 NPU） |
| LEVEL 3 | 离线保命 | 完全无网络 | 纯离线模式 | 基础（IMU + SOS） |

### 6.2 LEVEL 1：云端完整

网络畅通时，五个 Agent 全功能运行。视觉理解、OCR、人脸识别等重计算在云端完成，眼镜端仅负责传感器采集和语音输出。此模式下延迟最优（首字 < 500ms）、功能最全（五 Agent 全部可用）。

### 6.3 LEVEL 2：边缘降级

网络不稳定时（延迟 > 2s 或丢包率 > 30%），自动切换到端侧轻量模型。安全预警和场景感知由端侧 NPU 实时运行（YOLO-nano 目标检测 + 距离估算），导航降级为缓存模式（使用最近一次的在线路径 + 步数推算），社交 Agent 降级为端侧轻量 OCR。安全能力绝不中断。

### 6.4 LEVEL 3：离线保命

完全无网络时，系统进入纯离线保命模式。仅保留三项核心能力：

1. IMU 跌倒检测（纯端侧，不依赖网络）
2. 本地 SOS 呼救（通过蓝牙连接手机发送预设紧急联系人的短信/电话）
3. 最后位置缓存（GPS 最后已知位置存储在本地，网络恢复后同步到家属端）

一旦网络恢复，自动同步离线期间的告警日志到家属端 App。

### 6.5 降级触发与恢复

降级决策基于网络质量监控模块的实时判断：

- **降级触发**：连续 3 次云端 API 调用超时（> 2s）或丢包率 > 30%，自动降一级
- **恢复条件**：网络质量连续 10 秒稳定（延迟 < 500ms，丢包 < 5%），自动升级一级
- **安全 Agent 不降级**：A03 安全预警在所有等级下都保持运行，区别仅在于云端模型还是端侧模型

## 8. 隐私与安全

### 8.1 隐私设计四重保障

视障感知场景涉及大量个人敏感数据（摄像头画面、位置轨迹、人脸信息），隐私设计是产品的底线：

1. **边缘优先**：所有视觉数据优先在端侧 NPU 处理，仅当端侧模型能力不足时才上传云端。日常场景中 80% 以上的推理在本地完成，不上传任何图片。
2. **零留存**：云端处理的图片在推理完成后立即销毁，不存储、不用于模型训练。云端仅返回文本描述，不回传原始图片。
3. **人脸授权**：人脸识别功能需要用户主动开启。每张被记忆的人脸都需要用户通过语音确认"记住这个人"。用户可以随时说"忘记所有人脸"清除数据。
4. **物理遮挡**：镜架上配有物理摄像头遮挡盖。用户在私密场合（如家中、卫生间）可以物理关闭摄像头，此时系统仅依赖 IMU 和麦克风工作。

### 8.2 数据安全

- 所有本地数据使用 AES-256 加密存储
- 蓝牙通信使用 BLE 安全配对
- 家属端 App 数据传输使用 TLS 1.3
- 恢复出厂设置擦除所有数据（包括记忆库）

### 8.3 合规路径

- 3C 认证（电子产品强制认证）
- 残联辅助器具目录准入
- 个人信息保护法合规（数据最小化原则）
- 医疗器械分类评估（如涉及跌倒检测医疗级精度需求）

### 9.2 核心场景

**场景 1：早晨出门**

用户戴上眼镜走出家门。A01 自动播报："早安。今天多云，气温24度。门口路面干燥。左前方3米处有一辆共享单车，注意避让。电梯已到达本层。"

**场景 2：公交通勤**

用户走到公交站。A02 播报："路径已规划。请直行15步到达公交站。326路公交车预计2分钟后到站。"用户上车后，A02 持续播报到站信息。

**场景 3：安全预警**

用户正在过路口，A02 播报导航信息。此时 A03 检测到右侧电动车快速接近，距离 5 米。A03 立即抢占输出："注意！右侧有电动车快速接近，距离5米，请立即向左避让！"同时镜腿高频震动。用户停下脚步，电动车从右侧驶过。A03 播报完成后，A02 恢复被挂起的导航信息。

**场景 4：餐厅点餐**

用户走进餐厅，说"读一下菜单"。A04 识别菜单文字："红烧排骨饭 ¥28，宫保鸡丁饭 ¥22，番茄牛腩面 ¥18。"A05 注入记忆："上次您点过宫保鸡丁饭。"

**场景 5：社交相遇**

路上有人走来。A04 识别为人脸，与本地记忆库匹配后播报："前方是您的同事小王，正在向您挥手。"

**场景 6：夜间跌倒**

用户晚上在家中绊倒。IMU 检测到异常加速度冲击。10 秒倒计时后无人取消，系统自动发送 SOS 短信给女儿，附带 GPS 位置，并拨打电话。同时骨传导播报："已检测到跌倒，正在联系您的女儿。"
